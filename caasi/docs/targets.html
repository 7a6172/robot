Caasi v0.4.0 Targets: where work runs, and why caasi chose it

Targets & Selection

A target is anywhere work can run: this workstation, a robot, a GPU server, a simulation machine. Targets are declared in your configuration and addressed by name. Caasi discovers what each one actually has, checks it against what your work needs, and can choose among the ones that fit — always explaining the choice.

The target model

A target is a small block in ~/.config/caasi/config.yaml:

targets:
  my-robot:
    transport: ssh              # "local" or "ssh"
    host: 192.0.2.10
    port: 22
    user: someone
    deployment_root: /home/someone/caasi-deployments
    ssh_timeout: 20.0           # raise this on a relayed / VPN link
    tags: [robot, cpu-only, ros2]

  gpu-box:
    transport: ssh
    host: 192.0.2.20
    user: someone
    tags: [gpu, cuda]

The built-in local target always exists, so caasi is useful with no configuration at all. local is a deployed target like any other — see the deployment prerequisite for run below.

Tags are labels, not capabilities. A tag such as gpu is something you declare. Capabilities are discovered from the machine. Both are used, but they are not the same thing — and caasi never trusts a tag in place of a measured fact when checking requirements.

The target commands

CommandQuestion it answers
caasi target listWhat targets are configured?
caasi target inspect <t>What does that machine actually have — hardware, OS, ecosystem versions?
caasi target check <t>Is it reachable, and does it match what was declared about it?
caasi target selectWhich targets satisfy this project's requirements — and why not the others?
caasi target occupancyWhat is running where, right now?
caasi target runtimeWhat runtimes does it expose — processes, systemd, containers, ROS 2?

caasi node is an alias for caasi target.

Selection, and the three verdicts

Given a project whose manifest declares what it needs (requires:), target select evaluates every configured target and prints a verdict per target, with the measured fact behind it:

$ caasi target select
  Requires: ros2 jazzy, gpu

┃ Target    ┃ Verdict        ┃ Why                         ┃
┡━━━━━━━━━━━╇━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┩
│ robot-01  │ ✖ incompatible │ gpu: target reports no GPUs │
│ local     │ ● ready        │ 2 compatible                │
└───────────┴────────────────┴─────────────────────────────┘

Three outcomes are possible, and they are deliberately distinct:

VerdictMeaning
compatibleThe requirement is satisfied by a discovered fact.
missing / incompatibleThe target was asked, and does not have it.
untestedThe fact could not be measured — which is not evidence of absence.
The untested row is the most important idea in caasi. A fact nobody measured is reported as unmeasured. It is never silently rendered as a satisfied requirement or a failed one. Likewise, an out-of-range version produces a warning, not an outright incompatibility — caasi does not assert incompatibility from a version range alone.

target select is read-only and advisory. It reports; it does not choose. Nothing is deployed and no target is picked on your behalf.

Choosing with --where

Naming a target explicitly is the default and never changes:

caasi workload run <name> --target <target>

If you would rather let caasi choose among the targets that currently satisfy the workload, use --where:

caasi workload run <name> --where any           # any suitable target
caasi workload run <name> --where idle          # prefer one with no live runs
caasi workload run <name> --where prefer:gpu    # prefer a tag, among suitable ones

--target and --where are mutually exclusive, and one of them is required — there is no implicit default.

Every policy is explained. The decision report names the selected target, the policy and how it ordered the candidates, every eliminated target with the requirement and measured evidence that eliminated it, and any unmeasured or unknown conditions:

$ caasi workload run report --where prefer:cpu-only --dry-run
Selection for workload 'report'
  policy: prefer:cpu-only
  ordering: targets carrying tag 'cpu-only' first, then target name (matched)

  ✔ SELECTED   robot-01
     selected 'robot-01'; it satisfies the requirements
  ✖ eliminated local  suitable, but not chosen by this policy
Ordering is deterministic and stated, not hidden. Eligible targets are ordered by the policy key and then by target name. There is no scoring, no weighting and no load balancing — prefer:<tag> is a filter followed by name order, not a preference score.

When nothing fits

Caasi fails immediately, naming why each target was eliminated. It does not queue, wait, retry, or quietly pick something else:

$ caasi workload run impossible --where any
Selection for workload 'impossible'
  policy: any
  ordering: no eligible targets

  ✖ eliminated gpu-01  does not satisfy 'gpu' — target reports no GPUs
  ✖ eliminated local    does not satisfy 'gpu' — target reports 1 GPU(s), 4 required

Error: no target satisfies this workload (nothing was deployed or queued)

This is the boundary between selection and scheduling. Selection answers "which currently suitable target should I use?" A scheduler would answer "when and where should this eventually run?" Caasi implements only the former.

The deployment prerequisite for run

A run executes a deployed copy of the project, so run requires an active deployment — even when the target is local.

If you skip the deploy step, caasi refuses:

$ caasi workload run analyse --target local
✖ run — No active deployment found on target 'local' at
  '~/.caasi/deployments/local/my-project'. Run 'caasi deploy local' first.

This is deliberate. A workload that includes deploy before run is correct; a bare run is not. The refusal is informative on purpose — and the individual commands remain available so you can carry on by hand.

Occupancy: an observation, not a reservation

caasi target occupancy is read-only and answers what is running where:

StateMeaning
occupiedAt least one running or paused run (a paused process is still resident and still holding the target).
unknownNo occupying run, but at least one whose state could not be determined. Counted as neither busy nor free, and reported as such.
idleGenuinely nothing.
Occupancy does not reserve anything. Two commands started at the same moment can both see a target as idle and both select it. That is intentional: making --where idle a guarantee would require the reservation and scheduling machinery caasi deliberately does not have. See Limitations.

Runtimes: what the target exposes

caasi target runtime reports what a target is running, through each runtime's own native interface:

RuntimeCaasi asks
processps, falling back to /proc
systemdsystemctl, journalctl
containerdocker, or podman
ros2the ros2 CLI

When a runtime is absent, caasi says so and why rather than returning an empty list. You should never have to infer "there is nothing here" from "I got no rows back". The observability is read-only: caasi starts, stops and restarts nothing.
