Caasi v0.4.0 Deploy, build, and a persistent runtime that survives you

Deploy & Runtime Lifecycle

Getting software onto a target is one thing; making the target bring it up itself, and keeping track of which revision is running, is another. This page covers both: caasi deploy, target-native caasi build, and the caasi runtime lifecycle for a long-lived installation.

Deploy: getting the project onto the target

caasi deploy <target>                     # synchronise the project to the target
caasi deploy <target> --status             # what is deployed there now

The project is synchronised to the target's deployment_root. For the built-in local target, the destination is a dedicated sandbox (~/.caasi/deployments/local/<project>) rather than your working tree — which is why a local run still needs a deploy.

Deployment and your source tree are separate. Deploying does not modify your checkout, and caasi does not delete anything it did not put there. It also never rsync --deletes caasi's own runtime state, so a redeploy cannot silently destroy a deployment's rollback point.

Build: target-native, via colcon

caasi build --target <target>              # build the workspace ON the target
caasi build --target <target> --packages-select pkg_a pkg_b
caasi build --target <target> --jobs 4

The build runs on the target, in its own environment, using colcon — so it produces binaries for the machine that will run them. The build record is written at the deployment destination, which is where run then looks for it.

Where the build happens and which record it writescolcon, CMake, package discovery

The runtime lifecycle

A deployment puts files on a machine. A runtime is what makes those files an operational installation — something the machine brings up itself, without you logged in. That is a different problem, and it has its own commands.

caasi runtime install  <target>    # render the unit + environment, record the revision
caasi runtime enable   <target>    # systemctl --user enable
caasi runtime start    <target>    # systemctl --user start
caasi runtime status   <target>    # ask systemd what the state is
caasi runtime verify   <target>    # is the ACTIVE revision what caasi thinks it is?
caasi runtime update   <target>    # move to the newly deployed revision
caasi runtime rollback <target>    # return to the previous revision

Declaring one

# caasi.yaml
lifecycle: persistent
runtime:
  kind: systemd
  unit: my-robot.service
  entrypoint: ros2 launch my_robot bootloader.launch.py
  working_dir: .
  environment:                 # what the process needs to find ROS and the overlay
    - source /opt/ros/jazzy/setup.bash
    - source install/setup.bash
    - export ROBOT_MODE=real
  restart: on-failure

Two persistent concerns are declared separately, because they are genuinely different problems and conflating them makes an installation unverifiable:

ConcernHow caasi handles it
Environment persistenceDeclared and rendered into the form the target needs, rather than appended to a shell profile.
Service persistenceDeclared as an entrypoint; enablement and startup are delegated to the native mechanism.

Caasi is not a supervisor

Caasi renders the unit, installs it, and then asks systemd what the state is. It has no restart loop, no dependency graph and no process table of its own. systemd owns running the service; caasi owns identity, declaration, invocation, verification and provenance.

Revision identity, and an honest rollback

Each install records the deployment id, git revision and timestamp on the target, and retains the previous revision so rollback has something real to return to.

Rollback restores content; it does not merely relabel. It redeploys the recorded previous revision from your workstation, and it refuses when it cannot honestly restore that content:

$ caasi runtime rollback <target>
✖ rollback on <target>: workstation is at 5acfa0d... but the rollback target is
  3f06b5a...; rollback redeploys the previous revision from the workstation,
  so check out 3f06b5a... first

A rollback that could not restore the files but reported success anyway would leave the revision marker lying about what is running. caasi refuses instead.

What the runtime lifecycle does not do

  • It does not test your reboot. Whether a unit actually comes back after a reboot is a fact about your target's configuration; caasi can record and verify enablement, but it does not claim reboot survival it has not observed.
  • It is not a system-scope manager. The lifecycle targets user-scope units.
  • It does not delete. Rollback reinstalls a previous revision; nothing in the lifecycle removes a revision or a deployment.
