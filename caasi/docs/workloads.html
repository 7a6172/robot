Caasi v0.4.0 Workloads: declare the work, then let caasi run the chain

Workloads & Execution

A workload is the work a project wants done, written as data: what it needs, and the steps that carry it out. Running one composes operations caasi already has — deploy, build, run, collect — on a target, and records what happened.

Why a workload, not just a command

Without a workload declaration you would type each step by hand and carry the ids between them. A workload makes the sequence explicit, checkable, recordable and repeatable — and it is still only sequencing. It is not a workflow engine.

caasi workload run <name> --target <target>
caasi workload run <name> --where <policy>

Declaring a workload

# workloads/bringup.yaml
name: bringup
requires:                    # what this work needs, beyond the project's own requires:
  gpu:
    count: 1
    memory_gb: 8
steps:
  - deploy
  - build
  - run:
      config: experiments/bringup.yaml
  - collect
outputs:
  - path: "*.log"
    kind: logs
    destination: workstation

requires extends the project's own requires: from caasi.yaml. The two are merged, and the workload wins on a collision because it is the more specific statement of what this particular work needs.

The steps: a closed vocabulary

StepWhat it does
deploySynchronises the project to the target's deployment destination.
buildA target-native build — invokes colcon where the project has ROS packages.
runExecutes an experiment as a tracked run on the target.
collectFetches the artifacts routed to the workstation.

Two spellings are accepted — bare, or a single-key mapping for steps that take configuration:

steps:
  - deploy                                  # no configuration needed
  - run:                                    # configuration as a mapping
      config: experiments/job.yaml
The vocabulary is closed on purpose. An unknown step is rejected when the workload is parsed, not ignored — silently skipping a step you wrote would run a different sequence than your declaration says. There are no conditionals, loops, retries or branching. If a workload needs real control flow, that is a program, and the workload invokes it through run.

The composed chain

$ caasi workload run report --target local
Running workload 'report' on local
  ✔ deploy   — deployed deploy-demo-20261005-... (verified)
  ✔ build    — built on local
  ✔ run      — 20261006-...-report succeeded on local
  ✔ collect  — collected 1 artifact(s)

  produced: build_id=build-local-... deployment_id=deploy-...
            git_revision=... run_id=... run_status=succeeded run_target=local
✔ workload 'report' completed

A failing step stops the chain

The chain halts at the first failure and names the step, leaving the ids already produced visible so you can continue with the individual commands. Partial success is never reported as success:

$ caasi workload run failing --target local
  ✔ deploy — deployed deploy-demo-... (verified)
  ✖ run — run 20261006-...-broken failed (exit code 7)
✖ workload stopped at step 'run': run ... failed (exit code 7)
  the steps above it already ran; continue with the individual commands
  (caasi deploy/build/run)

Note the script's own exit code (7) is reported unchanged. If the run cannot be launched at all, that fails immediately — "the process was launched" and "the run succeeded" are different things, and caasi never conflates them.

Prerequisites the run step imposes

run requires an active deployment, even on the local target. A run executes a deployed copy of the project, so a workload that intends to run must include deploy first (or you must have deployed previously).

A build step likewise expects a deployment: it builds at the deployment destination, which is where run then looks for the build record.

The same thing, step by step

Composition is a convenience, not a replacement. Every step remains available on its own — which is what you use when something breaks:

caasi deploy <target>
caasi build --target <target>
caasi run start experiments/job.yaml --target <target>
caasi run artifacts <run-id> --collect

See Deploy & runtime lifecycle for the deployment and build steps in detail, and Runs & Logs for the run model.

Inspecting workloads

caasi workload list                # what work this project declares
caasi workload inspect <name>      # one workload's requirements and steps
caasi workload run <name> --dry-run --target <t>   # plan, without running anything

Who owns what

Caasi managesThe ecosystem owns
The workload declaration and its validationYour program and what it computes
Sequencing the steps and stopping on failurecolcon and the build system
Target selection, verification and provenanceROS 2 / DDS, Isaac, the runtime
Artifact routing and collectionWhat the files mean

The steps name operations caasi already has. There is no caasi build system, no caasi simulator and no caasi task runner underneath — see Examples to see the whole chain on real projects.
