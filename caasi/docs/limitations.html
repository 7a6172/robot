Caasi v0.4.0 What caasi does not do — and why that is deliberate

Limitations & What's Deferred

Knowing what a tool does not do is as useful as knowing what it does. This page separates three genuinely different things that are easy to blur together: environmental limitations, which are facts about the world; deliberate deferrals, which are choices caasi has made with reasons; and current boundaries, which describe the shape of the implementation.

None of the deferrals below is half-finished work. Each was assessed and left out on evidence. Caasi does not implement a capability merely because it appears on a roadmap — see what would justify revisiting them.

Environmental limitations

Facts about the world that caasi reports but does not paper over.

LimitationWhat it means
DDS discovery across a VPN A local GUI tool attaching to a remote ROS 2 graph depends on DDS multicast discovery traversing the network between the two machines. Across some topologies — two hosts on different LANs joined only by Tailscale, for instance — it does not, and the graph appears empty even though caasi resolved the context correctly.

Measured, not assumed: with a node genuinely running on the remote target (confirmed visible from the target itself) and a matching domain, a local query found no remote nodes — while local discovery on the same domain worked normally. The two machines were confirmed to be on different LANs, reachable only over the VPN.

This is a network and DDS fact, not a caasi defect. Caasi implements no DDS discovery, no tunnels and no multicast relays, and deliberately does not work around it — "fixing" it inside caasi would breach the boundary that keeps caasi thin.

Deliberately deferred

Capabilities that are not implemented and not planned for now, with the reason. These are decisions, taken against evidence.

DeferredWhy
Queues, scheduling, reservations, allocation A queue solves contention, and no contention has been observed: one developer, a small number of targets, ad-hoc runs. The inputs needed to detect contention already exist — caasi target occupancy reads live run state — so the cheapest honest answer is to report that a target is busy rather than to build machinery that reorders work invisibly. A queue without a scheduler is meaningless, and a scheduler designed without evidence would be designed against a guess.
Multi-target execution One workload, one target. Splitting a workload across machines needs a workload that genuinely must span them, which has not yet appeared.
Automatic forwarding If a target fails, nothing is silently re-run elsewhere. --where chooses before starting, never moves work mid-flight.
Retries and waiting When nothing satisfies a workload, caasi fails immediately with the reasons. Waiting would turn "nothing fits right now" into "something might happen later" — which is scheduling.
Ranking, scoring, load balancing Target ordering is deterministic and stated (policy key, then target name). There is no cost model and no hidden preference.
Fleet management Operating many machines as a fleet is a different problem from running a workload on a chosen one.
A monitoring web UI Planned as a small, observation-only interface. When it arrives, the CLI remains the control plane and it will have no deploy/build/run/stop controls. Not implemented yet.
Artifact destinations beyond two Results either return to the workstation or stay on the target. A third destination (an archive, a shared store, another machine) needs a transport that actually moves files; a name without a transport would receive nothing. See Runs & Logs.

Current boundaries

Where the implementation is deliberately narrower than it could be.

BoundaryDetail
Occupancy is an observation, not a reservation --where idle prefers an unoccupied target. Two commands started at the same moment can both see a target as idle and both select it. That race is intentional and unresolved: closing it would require exactly the reservation machinery that is out of scope.
Runtime lifecycle is user-scope The runtime commands target user-scope units. System-scope management is not implemented.
Reboot survival is not claimed Caasi can record and verify that a unit is enabled. Whether it actually comes back after a reboot is a fact about your target's configuration that caasi does not assert without observing it.
Unmeasured facts stay unmeasured A target fact that could not be discovered is reported as untested, never as satisfied or failed. This is a feature, but it means some verdicts are honestly inconclusive.
caasi remote is deprecated The legacy remote group predates targets. caasi target is the canonical model and remotes: configuration entries are imported as targets automatically. The group is retained rather than removed because remote connect and its path handling have no direct equivalent yet — removing it now would take away capability. Treat it as deprecated and prefer caasi target.
Not every command has a runnable example Destructive, physical, display-dependent and GPU-dependent commands are documented rather than demonstrated. See Examples.

What would justify revisiting the deferrals

So a future expansion is driven by evidence rather than by the wish to fill a roadmap:

  • Observed contention — queues and scheduling become worth discussing when machines are actually contended, which the occupancy query can show.
  • A genuine multi-target workload — work that truly must span machines.
  • A second real project — proof that the model generalises beyond one codebase.
  • Real artifact needs — a concrete requirement for a destination beyond the two that exist.
  • Real monitoring needs — usage that shows what a read-only view should show.

What caasi owns, and what it does not

Caasi managesCaasi delegates to the ecosystem
Project identity and layoutROS 2 / DDS — the middleware itself
Target identity, discovery and selectionssh, the network, the remote shell
Lifecycle intent, verification and provenancesystemd — running and restarting services
Sequencing the steps of a workloadcolcon / CMake — building
Artifact routing and collectionDocker/Podman — containers
Observation through native interfacesIsaac Sim / Isaac Lab — simulation and learning
Recording what happenednvidia-smi, RViz, ros2 — devices and tools

Caasi is not a ROS 2 replacement, a build system, a container runtime, a service manager or a simulator. When an existing tool already solves something well, caasi exposes and invokes it rather than rebuilding it.
