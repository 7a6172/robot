ROS 1 → ROS 2 Parity Audit

A complete line-level audit of the migrated stack, using the ROS 1 Noetic tree as ground truth. Because the real robot was not yet available, the goal was to be as sure as possible now: every config value, launch argument, message field, driver parameter and build flag was compared between the two trees. The audit found 8 defects; all 8 were fixed and re-validated.

1. Scope & method

Ground truth: openmover_robot/openmover_ws/src (ROS 1 packages) plus the repo-root runtime config openmover_robot/config. Target: openmover_ws/src (ROS 2). Four read-only audit tracks ran in parallel:

TrackWhat was compared
Messages & drivers All .msg/.srv definitions field-by-field; bluesea2 LiDAR driver parameters (IPs, ports, RPM, angle filter, inversion); ira_laser_tools merger configuration.
Robot core (openmover) Every launch file and every YAML in config_defaults/ against the ROS 1 runtime config; mode-server logic; HAL Python nodes; C++ handlers (navigation, mapping, auto-mapping); URDF and meshes.
Algorithm toolboxes auto_mapping_toolbox and relocalization_toolbox: sources, CMake flags, service interfaces, parameter usage.
Simulation + build hygiene warehouse_simulation world, bridge, nav2 params, tests; install-tree hygiene (stale artifacts, dangling references from removed features).

Each track reported: defect (behavior diverges from ROS 1), minor (cosmetic / dead config), or faithful (parity confirmed). All defects below were fixed in the same session and re-validated.

2. Findings & fixes

A — Costmap observation sources dropped during config merge defect

ROS 1 kept full global_costmap: sections in navigation.yaml / mapping.yaml. During the ROS 2 config merge these sections were not carried over, so the in-process nav2_costmap_2d instances inside navigation_handler / auto_mapping_handler ran with default-only sensor configuration.

Fix: the ROS 1 values were ported verbatim (nav2 plugin syntax): static_layer (map_topic: /openmover/mapping/map) + obstacle_layer observing /openmover/hardware/lidar/scan, with the ROS 1 ranges — navigation: obstacle_range 2.5 / raytrace_range 3.0; mapping: 4.5 / 5.0, track_unknown_space and unknown_cost_value -1 only in mapping mode. Top-level sections route to the child costmap nodes by base-name matching (constructor verified in nav2_costmap_2d/costmap_2d_ros.hpp). Files: config_defaults/apps/navigation/navigation.yaml, config_defaults/apps/mapping/mapping.yaml.

Parity note

In ROS 1 these sections were consumed only by an orphan handler (global_planner_handler.cpp, never launched) — i.e. dead config. The ROS 2 merge activated the capability but dropped the config; porting the YAML keeps the newly-active costmaps tuned exactly as the original authors intended.

B — map_server never left “Unconfigured” defect

nav2_map_server is a lifecycle node; launched as a plain node it stays in the Unconfigured state and never publishes the map. ROS 1's map_server had no lifecycle, so nothing in the original port triggered the transitions.

Fix: added a nav2_lifecycle_manager (lifecycle_manager_mapping, autostart: true, node_names: ['map_server'], bond_timeout_ms: 4000) to launch/modules/mapping/map_server.launch.py, and declared <exec_depend>nav2_lifecycle_manager</exec_depend> in package.xml. The include is only reachable from bootloader.launch.py, so no name collisions with the warehouse demo's own navigation lifecycle manager.

C — package://ssir2 remnants in URDF defect

urdf/environment_description.urdf still referenced package://ssir2/meshes/environment_description/base_link.STL in both the visual and collision geometries — a package that does not exist in the ROS 2 workspace, so robot-state publishing of that link would fail mesh resolution.

Fix: repointed both to package://openmover/meshes/environment_description/base_link.STL (mesh confirmed present in the package).

D — get_navigation_state cleared its buffer defect

The ROS 2 port of scripts/hal/protocol.py set the shared buffer to None after reading it. ROS 1 semantics are read without clearing (retain the latest state), so a second query right after the first would wrongly return nothing.

Fix: restored retain semantics — the buffer is copied under the lock and returned, never cleared, matching ROS 1 line-for-line.

E — relocalization_toolbox lost its optimization flags defect

The ROS 1 CMakeLists compiled the toolbox with -O3 -flto -ffast-math -funroll-loops because relocalization scoring/sampling is a compute hotspot. The ROS 2 port only kept -Wall -Wextra, producing a measurably slower node.

Fix: restored the exact flag set (plus -flto link option) in relocalization_toolbox/CMakeLists.txt and rebuilt successfully (only benign sign-compare warnings).

F — misleading nav2_params header comment minor→fixed

warehouse_simulation/config/nav2_params.yaml carried a header comment claiming values were copied from the robot config, which was no longer accurate after tuning. Fix: comment rewritten to describe what the file actually is (the warehouse-demo Nav2 parameter set).

G — actor comment overstated parity minor→fixed

The pedestrian-actor comment in warehouse_simulation/worlds/warehouse.sdf claimed full waypoint parity with ROS 1, but the z coordinate was intentionally raised from 0 to 1.0 for the gz Harmonic actor skin anchor. Fix: comment now states exactly that: x/y and timing match ROS 1, z was lifted, and actors have no physics collision body (avoidance happens via the LiDAR → costmap path).

H — stale __pycache__ in install tree minor→fixed

Stray __pycache__ directories had accumulated in the workspace during test runs. Fix: removed; builds use --symlink-install so Python sources stay live and no caching is needed.

6. Helper scripts

Three scripts in openmover_ws/tools/ automate the environment checks and dependency installation described in Getting Started. All are safe to re-run at any time; check_system.sh is strictly read-only.

ScriptWhat it does
tools/setup.sh Interactive setup wizard: detects OS/ROS/Gazebo/RAM/GPU/disk, reports whether the machine is sufficient, proposes a build-parallelism tier sized to RAM (32 GB+: parallel, 16 GB: 2 jobs, less: 1 job), then offers to install dependencies, build the workspace and run tests — each behind a yes/no prompt. Flags: --check (detection only), --yes, --jobs N.
tools/check_system.sh Verifies OS release, ROS 2 Jazzy, gz-sim, the apt dependency set, the OSQP install, GPU presence and free RAM, then prints a PASS/WARN/FAIL summary. Exit code 0 means the machine can build and run the workspace.
tools/install_deps.sh Installs the apt packages, runs rosdep install over the workspace, and builds/installs OSQP from tools/osqp_build if it is missing. Uses -j2 for the OSQP build to respect the memory constraint. 
# from the workspace root
bash tools/setup.sh             # interactive wizard (recommended)
bash tools/check_system.sh      # read-only health check
sudo bash tools/install_deps.sh # installs system dependencies
