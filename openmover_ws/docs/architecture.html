System Design

Architecture

How the migrated system is organized: the two stacks, the runtime orchestration (HAL + mode servers + launch manager), the node/topic/TF layout, and the design patterns used to replace ROS 1-isms.

The two stacks

The workspace contains two independent, runnable stacks that share message and toolbox packages. Both preserve the ROS 1 topic, service, TF-frame, and parameter names so behavior stays directly comparable with the original.

1. Robot core — openmover

  • HAL / workload orchestration (Python)
  • 5 mode servers that start/stop launch subtrees at runtime
  • Hardware drivers (motor, IO board, simulation)
  • Cartographer SLAM & localization
  • Custom navigation stack (costmap-as-library)
  • Auto-mapping (frontier exploration) + relocalization toolboxes

2. Warehouse demo — warehouse_simulation

  • Gazebo Harmonic world (workcell + bins + 2 walking actors)
  • Pioneer3DX model with gz diff-drive + gpu_lidar
  • ros_gz_bridge for clock / scan / odom / cmd_vel / tf
  • slam_toolbox async mapping (replaces gmapping)
  • Nav2 full stack (replaces move_base)
  • trajectory_server + cmd_vel watchdog + key teleop

Robot core: runtime orchestration

The entry point is workload.launch.py, which includes bootloader.launch.py and starts the business-orchestration node workload.py. The bootloader starts the mode servers, visualization, the hardware bring-up, and rosbridge.

Mode servers & the launch manager

Five Python servers dynamically start/stop launch subtrees at runtime. In ROS 1 they used the roslaunch Python API; in ROS 2 that API does not exist, so a subprocess-based launch manager was introduced (openmover/scripts/launch_manager.py). It wraps subprocess.Popen(["ros2","launch",...]) with start / stop (process-group kill + grace period) / restart / liveness. The servers keep their exact ROS 1 service interfaces and parameter names.

Robot core: functional chains

Localization

motor_handler / simulation_handler publish odometry to localization_handler, which fuses pose and broadcasts the odom→base_link TF. Cartographer supplies the corrected pose via tracked_pose (remapped to pose_aft_mapped) and the map→odom TF. localization_confidence_handler scores scan-vs-map; relocalization_2d_handler provides global relocalization.

Mapping

Cartographer (mapping.lua) builds the map; auto_mapping_handler explores frontiers using its own costmap + Dijkstra/OSQP planner; navigation_handler executes the generated paths. Saving uses cartographer WriteState (.pbstream) plus nav2_map_server map_saver_cli (pgm/yaml).

Navigation

navigation_handler is the largest node (~50 parameters). It uses nav2_costmap_2d::Costmap2DROS as a library (two instances: global_costmap and global_costmap_static), a custom local planner (mover / path_follower / path_checker / collision_checker), and exposes nav_msgs/srv/GetPlan at openmover/navigation/global_planner/make_plan (the former orphan global_planner_handler merged in).

Pedestrian avoidance (perception-based)

Design

The two walking actors in warehouse.sdf have no physics collision proxy. Gazebo Harmonic actors are visual-only. Instead the robot perceives them: the LiDAR returns hits on the actor mesh → they appear in the local costmap as obstacles → Nav2 stops / waits and resumes after the actor clears the path. This matches how the real robot avoids a moving person. An earlier “proxy box” approach was removed as a simulation-only hack.
