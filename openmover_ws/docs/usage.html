Run Book

Usage

Step-by-step instructions for running the warehouse simulation, driving the robot, watching pedestrian avoidance, and starting the robot-core stack in simulation or on hardware.

Before every run

Make sure no stale Gazebo or ROS processes are left over from a previous session — a new launch can silently attach to an old server and show the wrong world:

pkill -f "gz sim"; pkill -f ruby; sleep 2; ps aux | grep -E "gz sim|ruby" | grep -v grep

1. Warehouse simulation (recommended first run)

This is the validated end-to-end demo. In terminal 1 start the full stack (Gazebo + bridge + slam_toolbox + Nav2 + rviz2):

source /opt/ros/jazzy/setup.bash
source ~/openmover_ws/install/setup.bash
ros2 launch warehouse_simulation warehouse_simulation.launch.py

Available launch arguments:

ArgumentDefaultMeaning
use_sim_timetrueUse the Gazebo clock bridge
rviztrueStart rviz2 with the demo config
headlessfalseRun the Gazebo server only (no GUI) — for low-power hosts
x_pos / y_pos / z_pos0.0Robot spawn position (matches ROS 1)

In terminal 2 start keyboard teleop:

source ~/openmover_ws/install/setup.bash
ros2 run warehouse_simulation key_control

Drive with the arrow keys: hold a key to keep driving — commands repeat at 20 Hz while it is held, and the robot auto-stops when you let go. UP forward, DOWN reverse, LEFT/RIGHT rotate, q quits. As an extra safety net, cmd_vel_watchdog also sends zero velocity 0.4 s after the last command.

Sending a Nav2 goal

In rviz2 select the 2D Goal Pose tool and click on the map. Nav2 plans with NavfnPlanner and drives with the MPPI controller while slam_toolbox keeps updating the map.

Watching pedestrian avoidance

Verified behavior

Two actors walk fixed routes across the warehouse. Drive (or send a goal) so the robot's path crosses an actor. The LiDAR sees the actor's legs, they appear as a red/occupied region in the local costmap, and Nav2 slows, stops, and waits. Once the actor clears the path the robot resumes. This is perception-based — there is no physics proxy — exactly how the real robot will avoid a moving person.

2. Inspecting the running system

ros2 topic list
ros2 topic hz /scan                # lidar rate
ros2 topic echo /cmd_vel            # commanded velocity
ros2 node list
ros2 run tf2_tools view_frames      # TF tree -> frames.pdf
ros2 lifecycle get /slam_toolbox    # should reach active

3. Robot-core stack (openmover)

The production stack is started through workload.launch.py (which includes the bootloader). Choose simulation or real-hardware mode with system_mode.

Simulation mode

source ~/openmover_ws/install/setup.bash
ros2 launch openmover workload.launch.py system_mode:=0

This brings up the HAL, mode servers, cartographer, the laser merger, rviz2, and rosbridge (port 8080), with the simulation odometry source and the openmover simulation world.

Real-hardware mode

source ~/openmover_ws/install/setup.bash
ros2 launch openmover workload.launch.py system_mode:=1

This switches bring-up to the real drivers: two bluesea2 LiDARs (192.168.100.101/.102), the motor controller (192.168.100.100:23), and the IO board (192.168.100.100:26). See Hardware for the network layout.

Real robot

The real-robot branch is migrated and configured but not yet tested on hardware. Before first physical use: verify the network addresses, ensure the e-stop is reachable, and run in an empty area. This documentation reflects simulation-verified behavior.

4. High-level workflow (HAL scripting)

The robot's behavior is orchestrated by the Python HAL. Rather than calling individual topics, you script against hal/cli using the service layer. A typical flow (mirrors the ROS 1 scripted test):

  1. Start in manual mode and teleop to position the robot.
  2. Switch to mapping mode (set_func_mode → create_map) and drive to build a map; auto-mapping can drive for you.
  3. Save the map (cartographer WriteState + pgm/yaml).
  4. Switch to localization mode on the saved map; issue an initial pose.
  5. Switch to navigation mode and send a goal with navigation/request; monitor navigation/state until reached.

These steps are exposed through the services listed in Architecture. Interactive scripts import the hal and cli modules from the installed openmover scripts directory.

5. Keyboard teleop alternatives

  • Warehouse demo: ros2 run warehouse_simulation key_control (ported, same key semantics).
  • Any robot: ros2 run teleop_twist_keyboard teleop_twist_keyboard with the command topic remapped to the robot's cmd_vel.
  • Openmover manual mode uses cmd_vel_mode/request + cmd_vel_manual (HAL-driven), matching ROS 1.
Manual mode has no avoidance

As in ROS 1, manual/teleop driving is raw — obstacle avoidance is only applied in autonomous navigation modes. This is intentional parity, not a bug.
