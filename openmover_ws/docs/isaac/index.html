OpenMover — Isaac Sim Integration

Isaac Sim now drives the OpenMover robot stacks over ROS 2 topics, with the stacks unmodified. Isaac plays the role Gazebo used to play — it takes velocity commands and publishes /clock, odometry and two bluesea2-style 2D LiDAR scans — so both the warehouse demo stack (slam_toolbox + Nav2) and the real product stack run against a raytraced, physics-accurate warehouse workcell. The AI-agent companion to this page lives in docs/isaac/00_START_HERE.md (5 files).

Steps 1.0–1.5 complete, all gates passed: headless smoke test, drivable robot import, RTX LiDAR mirroring the bluesea2 chain, bridge core, warehouse scene, and stack integration for both stacks. Teleop works end-to-end in Isaac against the real product stack; Nav2 navigation was verified against the warehouse stack.

What was built

🤖

Robot in Isaac

Pioneer 3DX imported from URDF to USD, driven by a velocity servo on the two drive wheels. Ground-truth odometry exposed to ROS.

📡

LiDAR mirror

Two RTX raytraced 2D LiDARs matching the real bluesea2 chain: 600 samples, ±90°, 0.22–10 m, 15 Hz, front/rear mounts.

🏭

Warehouse scene

Workcell collision boxes baked from the Gazebo SDF plus the converted visual mesh for raytracing. Robot spawns at the Gazebo spawn pose.

🔗

Two ROS 2 bridges

One per stack, both running inside Isaac’s Python process (rclpy, no external bridge binary), real-time paced.

Why ROS 2 matters here

The decision to bring Isaac up over ROS 2 (rather than a proprietary or ROS 1 interface) is load-bearing for this project:

ReasonWhat it gives us
Isaac Sim is ROS 2-native Isaac Sim 6.0 ships without the legacy ROS 1 bridge. Its bundled Python runs rclpy directly, so the bridge is a plain script inside the simulator — no extra process, no code generation, no version glue.
Sim–real parity The product stack was migrated to ROS 2 Jazzy. Isaac plugs into the exact topics the real hardware uses (openmover/control/cmd_vel_sim in, openmover/hardware/odom_sim + scans out), with simulation_handler standing in for motor_handler untouched. What is validated in Isaac is the real code path.
DDS discovery Publishers and subscribers find each other with zero configuration. The simulator and any number of tooling nodes (teleop, rviz, recorders, test scripts) join the same graph just by being on the LAN.
Networked / tethered deployment Because everything is DDS topics, Isaac can run on the workstation while the stack runs elsewhere — on the robot, on a tethered laptop, or split across machines — without changing a line. This is also how the future learning pipeline will connect: method nodes speak standard /scan in, /cmd_vel out.
For other systems Any ROS 2 robot stack gets the same deal: the simulator seam is a short, well-known topic contract (the gz_bridge.yaml), so swapping Gazebo for Isaac is a bridge script plus one launch gate — not a re-architecture.

Architecture & data flow

Stack A — the product stack (openmover)

Isaac mirrors config_defaults/gz_bridge.yaml exactly. No TF comes from Isaac: localization_handler owns odom→base_link, exactly as with the real Gazebo chain (publishOdomTF=false).

DirTopicTypeConsumed by

The only ROS-side change (approved): a launch_gazebo argument (default 1) on bringup.launch.py/bootloader.launch.py. With launch_gazebo:=0 the Gazebo simulator, bridge and spawn are skipped and Isaac takes their place — every other sim node runs exactly as before. system_mode semantics are untouched, so no handler code needed edits.

The sim loop

60 Hz physics, 15 Hz scan tick. Rendering (the dominant cost) is gated to the scan tick; the loop is paced to real time; pending ROS callbacks are pumped each iteration with rclpy.spin_once(node, timeout_sec=0) (rclpy has no spin_some). Instrumentation (heartbeat, loop-exit report, traceback dump) is kept in both bridges on purpose — it is what made the hard bugs diagnosable.

Known caveats & follow-ups

RAM

16 GiB machine with a freeze history: every Isaac script preflights RAM (abort < 8 GiB, warn < 12.5 GiB), and the bridge RSS grows during long runs — restart it between sessions.

  • Isaac drives the Pioneer 3DX asset kinematics (0.32 m / 0.09 m) while the openmover Gazebo DiffDrive uses 0.324 / 0.05035 — accepted for bring-up (Isaac is internally consistent); importing the openmover URDF is a follow-up.
  • RTX LiDAR ranges read ~0.1 m short of geometric truth (asset offset); characterised, not yet compensated.
  • obstacle_handler can hit a TF race at boot (FATAL, no respawn); restart it ~10 s after bring-up — see runbooks.
  • Isaac is 6.0.1-rc.7; stable 6.0.1 is the drop-in fallback.
